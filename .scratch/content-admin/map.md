# Wayfinder map: Content Admin

Label: wayfinder:map

## Destination

v1 Admin live at `/admin` on the deployed site: staff sign in with the shared password, edit News & Announcements plus the five existing content files (home, governance, faculty, placements, departments), upload images and PDF attachments (immutable keys), manage gallery folders, and clean up orphan assets — every save publishing as a commit to `main`.

## Notes

- **Execution override**: this map carries the build. Tickets include execution slices, worked one per session, until the destination is reached.
- **Design foundation** (settled by the 2026-08-08 grilling session — read before any ticket): [`CONTEXT.md`](../../CONTEXT.md) for vocabulary, and ADRs [0001 content-edits-are-git-commits](../../docs/adr/0001-content-edits-are-git-commits.md), [0002 shared-password-auth](../../docs/adr/0002-shared-password-auth.md), [0003 immutable-asset-keys](../../docs/adr/0003-immutable-asset-keys.md).
- Skills: HITL tickets use `/grilling` + `/domain-modeling`; consult repo skills `asset-pipeline` (R2 pipeline) and `prod-ready` (page standards) where relevant.
- Standing constraints: $0 beyond the existing Vercel plan; R2 bucket stays under the 10GB free tier; Zod is the single content contract (loader + build + admin save all enforce it); last-write-wins on concurrent saves (no conflict UX, deliberate).
- **The agent never commits or pushes** — each slice is left as working-tree changes for Pratik to review and land.
- Zod schemas are written from what loaders/pages actually render — the existing `*.schema.json` files are unreliable and become generated output of Zod.

- [Cleanup and usage screen](issues/12-cleanup-usage-screen.md) — **BUILT** (uncommitted): `/admin/cleanup` reads **8.36 GB of 10 GB (81.6%), 2,957 files, 81 unused, 153.5 MB reclaimable, 0 broken references** against the real bucket — the unused list almost entirely superseded PDFs under `documents/`, exactly what [10](issues/10-orphan-detection-study.md) predicted. "Is this file used?" cannot be answered from a deployed function, which has no source tree, so the code scan runs at **build time** into `src/data/asset-references.ts` (467 literal keys) and the screen unions it with the content files *this deployment shipped* and the content files *at repo HEAD* — the third because an Editor who publishes a photo at 10:00 has changed HEAD and the deploy carrying it does not exist for two more minutes. Keys are matched by shape and set-membership, never by field name, so an unschema'd field holding a photo cannot silently unprotect it. Two reference kinds are unreadable by any scan — `assetsUnder("folder/")`, where the folder *is* the reference, and `` asset(`hostels/${block}/${key}.webp`) ``, where the key exists nowhere as text (80 live files) — so 17 folders are protected by hand with a stated reason each, and because such a list is one refactor from being wrong **the same scanner runs as a build step and a test**: a new unprotected `assetsUnder(...)`, or a new file that builds a key from a template literal, fails `pnpm build` and `pnpm test` by name (proved by adding both and watching it refuse). Everything fails towards keeping the file: a reference set under 1,000 is treated as a broken scan and reports nothing rather than an empty, reassuring list; 30 days' grace because bytes land on R2 before the Publish that references them; extensionless keys are folder markers; both mutating steps recompute the unused set from a fresh sweep, so the request says *which* of the offered files, never *that* they are removable; cap 25, and never >5% of the bucket. [10]'s two-phase delete **is** the shape of the screen — button one commits the manifest without those keys (revertible, ends in the same "saved → live" wait, because the wait is the point), button two deletes the bytes behind a confirm and **only for keys the manifest no longer mentions**, refusing a still-registered key by name so a deploy has to go out in between. All 81 candidates today are registered, so it offers step one and refuses step two, which is the correct first state. One `ListObjectsV2` sweep feeds the gauge, the reclaimable figure and the grace window (nothing records object sizes), and gives drift both ways — `manifest ∖ bucket` is a separate, louder card, because an entry with no bytes behind it is a live page drawing a broken image. 329 tests, tsc + eslint clean. **The orphan list was checked against a naive grep of every source and content file: 0 of the 81 is referenced anywhere**; the four that share a *file name* with something in use are all genuine. Seven refusal paths exercised against the running route, and **the R2 delete path was executed end to end** on a throwaway object (uploaded, found in the sweep, deleted, confirmed gone). Still unexecuted: the unregister commit, which writes to `main`. Side flag: `scripts/upload-assets.mjs --prune` is a bigger bulk-deletion footgun than this screen — no cap, no confirm, no two phases.
